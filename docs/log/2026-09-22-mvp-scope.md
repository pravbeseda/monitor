# 2026-09-22 — MVP scope

The POC closed, and the roadmap's next stage was the MVP: "5–7 metrics from different
domains, declarative config, digests". Digests and declarative metrics
([0032](../decisions/0032-thresholds-are-set-in-the-interface.md),
[0033](../decisions/0033-a-subject-is-a-series.md)) already existed, so the stage came down
to which metrics.

## Skins first — rejected for now

Mission control is empty while all is well and surfaces anomalies on its own; it needs
anomaly rank, trend and health, and the State API carries levels only. With one metric
there was also nothing for a skin to arrange. A thin board over levels was possible, and
rejected as work the semantic engine would redo.

## Manual input — deferred

The concept called manual input "a feature, not a crutch" and put finance and health on it.
The user sees no value in typing metrics in, so the MVP carries none, and those domains
wait for sources that report on their own (a health export, an external finance sensor).
Both were weighed and left for later: each costs more than the infra sensors together and
brings one domain with one or two series.

## Backups — deferred

The reading that fails silently, and the one that needs a parameter: a sensor configured by
`interval` alone cannot say which file to watch. That extends the contract of
[0010](../decisions/0010-agent-configuration.md) and deserved its own discussion:
[#51](https://github.com/pravbeseda/monitor/issues/51).

## What the spec reviews changed

- **A new default below a file's tick would have crashed an upgraded hub.** The interval
  check refused any sensor faster than the node's `base_tick`, and a hub that upgrades itself
  hourly meets its file unattended. Defaults of 5m broke a file with a 15m tick; moving them
  to 15m still broke one whose laptops tick hourly, which the old 1h disk interval allowed.
  So the check now refuses only an interval the file wrote, and a compiled-in one below the
  tick is raised to it. Picking slower defaults instead would have guessed at every file's
  tick and chosen the sampling rate for it; with the raise in place, `load` and `memory`
  went back to 5m, since they move faster than the rest.
- **A Mac has no "available memory" of its own.** Activity Monitor's figure rests on app
  memory, which no public interface reports, and a reconstruction of it read a fraction of
  what the kernel reported free on the same machine. The kernel's `kern.memorystatus_level` is the
  figure its own memory-pressure decisions use, so it is the one reported — as a share, with
  bytes derived — and it needs no cgo.
- **`systemd` enabled on a machine without it** would have logged an error every interval,
  since the agent runs every enabled sensor whatever its manifest says. It stays quiet.
- **A file that writes `profile: [disk]`** — as the example did — replaces the compiled-in
  profile, so such a deployment gets no new sensor until the line changes; install.md says so.
- **Growing a compiled-in profile looked like it broke
  [0010](../decisions/0010-agent-configuration.md)**, which says a new sensor never switches
  itself on across the fleet. It does not: 0010 rejects sensors that are on by default, and
  requires a sensor to enter a profile deliberately. Adding the host sensors to the `server`
  and `laptop` profiles in a reviewed release is that deliberate step — 0010's own example
  profiles list memory and load — and a class whose file writes its own profile keeps it.
