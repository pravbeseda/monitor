# 2026-09-19 — State API and the debug view

The POC items were done, and the next step toward skins was chosen: the State API and the
debug view come before the MVP metrics and the semantic engine. The reasons were:

- the debug table is cheap;
- `/api/v1` takes additive fields;
- a real consumer shows what the contract lacks sooner than a complete spec would.

The risk is that the contract is shaped by one metric (disk).

## Settled in the spec reviews

- **`readings`, not `series`.** `series` already names a different shape in
  `/api/v1/history`. The first draft also nested `value` inside a `value` object.
- **`stale: null` for a reading no freshness rule applies to.** Saying `false` would claim that
  values from a decommissioned node, or from an undeclared metric, are current.
- **`configured` on a node.** Otherwise `level: null` would mean both "not judged yet" and
  "no longer in the configuration".
- **Stale removable volumes are listed.** The first draft left them out of the endpoint. That
  contradicted history.md, which says only `/` leaves them out, and it would have kept a
  "detached backup drive" from ever reaching a skin.
- **A node's level ignores stale subjects.** This was the user's choice among three options.
  The other two were counting every subject, and ignoring only stale removable volumes, which
  would move a page rule into the core. This matches the digest.
- **Subject order is stated by the spec, not inherited from evaluation.** Evaluation breaks
  ties on the JSON-encoded labels, while the API uses history's `key=value` rendering. A
  node's silence subject comes first even beside a volume that reports no mount.

## Found on the way

An unreadable stored level is never replaced while its subject stays `ok`
([#41](https://github.com/pravbeseda/monitor/issues/41)). The state reports such a subject
as `level: null` until that bug is fixed.
