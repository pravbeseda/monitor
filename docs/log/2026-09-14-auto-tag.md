# 2026-09-14 — A merge tags itself: what lost

Context: [release.md](../specs/release.md#tagging-a-merge). Releasing was already automated
from a tag; the question was only who pushes the tag.

## How the tag reaches the release workflow

A tag created with a workflow's own `GITHUB_TOKEN` starts no other workflow, so the tagging
run starts the release with `workflow_dispatch` on that tag, the one event that token may
trigger. The run sees the tag as its ref, so the `release` environment's `v*` tag policy
admits it unchanged.

- **A GitHub App or a personal token pushes the tag** — rejected: `release.yml` would need no
  change, but that token is a long-lived secret that can push a `v*` tag, which is to say it
  can sign. One trigger line is not worth a second signing credential in a public repository.
- **release-please** — rejected: it needs conventional commit subjects the history does not
  keep, commits a changelog and a version file, which breaks "no source edit is part of
  releasing", and adds a third-party action for batching nobody asked for.
- **A "Release" button that computes the next version** — rejected: it is still a person
  choosing the moment, one click instead of `git tag && git push`.

## Choosing the version

Labels on the pull request rather than commit subjects: merges here are merge commits with
free-form titles, and a label can be changed after review without rewriting history. No label
is a patch release; `release:none` opts out.

Accepted with that default: every merge ships a new newest release, and under
[0022](../decisions/0022-updates-are-pulled.md) point 6 every machine's stub runs the
installer from the newest release whatever the hub's target. The hub's target holds back the
binaries, not that installer. This was weighed when the option was chosen.

Every `v*` tag in the repository counts toward the highest version, not only those on `main`:
a version that skips past a stray tag is harmless, while ignoring one could choose a tag that
already exists.

## Merges in quick succession

The tagging runs share one concurrency group with `queue: max`. The default queue keeps one
waiting run and replaces it with the next, so of three quick merges the second would get no
tag and lose its label; a `release:major` could ship as a patch. actionlint 1.7.12 does not
know the key yet, while GitHub's workflow syntax documents it.

## Switching it off

`gh workflow disable auto-tag.yml` rather than a repository variable read by the workflow: it
is GitHub's own switch, needs no code, and shows as disabled in the Actions tab. Pushing a
tag by hand never stopped working, so manual releasing needs nothing else.

Merges that touch only documentation are filtered with `paths-ignore` on the push, so they
start no run at all.
